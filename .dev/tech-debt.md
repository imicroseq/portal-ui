# Tech debt

Known issues, scope-adjacent problems, and deferred work. Format per `conventions/session-discipline.md` § Tech-debt entry format.

`global/utils/arrangerExport.ts`'s `resolveExportColumns` duplicates `@overture-stack/arranger-components`'s own internal `saveTSV` column-customizer logic verbatim (not part of that package's public API, confirmed by tracing its real source). It exists because the "Metadata only" download exporter needs to fire a `file_download` tracking event, and `{ function: 'saveTSV' }` accepts only one callback, so the shorthand had to be replaced with a function that reproduces what it does. This can silently drift from Arranger's real behavior if that internal logic ever changes with no corresponding public API change to notice.
fix: remove `resolveExportColumns` once Arranger ships either a public `onExport` hook (fired for any exporter, built-in or custom) or exports `saveTSV` directly; both were raised with an Arranger-focused peer session and logged on their end as an open API decision, not committed yet. Until then, re-check this function against Arranger's source on any `@overture-stack/arranger-components` upgrade that touches `Table/DownloadButton`.

The clinical archive-build/download path has no authentication anywhere along it: `saveSet` (Arranger GraphQL mutation via `components/utils/arrangerFetcher.ts`) and `startArchiveBuildBySetId` (`global/hooks/useSingularityData/index.ts`, a plain `fetch` to Singularity) both send only `Content-Type`, and the resulting download is a bare `window.location.assign` to `/download/archive/{archive.id}`. An authenticated fetcher already exists (`fetchWithAuth` in `global/hooks/useAuthContext.tsx`) but neither call imports or uses it. Surfaced during an Arranger-side design review of sets/access-control (`sets-consumer-singularity.md`); Singularity's own `/archives` listing is reportedly an unauthenticated paged endpoint, making completed archive IDs enumerable, though that surface belongs to Singularity, not this repo.
fix: confirmed intentional by Andy (2026-08-25): fully open data serving is correct for now. Ongoing work with Usher and Arranger is expected to change this later; revisit once that work lands rather than treating this as an active gap to close now.
standalone: yes

`components/pages/clinical/RepoTable/helper.ts`'s `saveSet` call passes `path: "name"` to Arranger's `saveSet` mutation as a literal, silently relying on Arranger falling back to the document's `_id` when that path resolves to nothing. Confirmed via git archaeology this is unexamined copy-paste boilerplate, not a deliberate choice: introduced in `1f4aa5c0` ("Set download #85", 2021-08-25) with zero mention of `path` in that commit's message, then carried forward unchanged through five later refactors. Confirmed via the clinical Arranger config (`virusseq-infra-sd4h`, `documentType: "file"`, index `clinical_centric`) that there is no top-level `name` field on that document at all, every "name"-containing field is nested (`file.name`, `repositories.name`, etc.) — so the fallback isn't an edge case, it's the only path ever exercised. Confirmed with a Singularity-focused peer session tracing Arranger's actual `resolveSets.js` that the fallback (lodash `get`'s default) fires only when the resolved value is `undefined`, not `null` or an empty string, and that Singularity's `size: ids.length` check does not catch a partial population either (a mixed name/id/null array still reports the correct size, so that check alone can't distinguish it from a healthy set).

Two separate triggers, not one, both confirmed by that same peer session tracing the actual code:

1. **A top-level `name` field gets added to the clinical index mapping and populated.** Sets begin storing names (or a mix of names/nulls/ids if only partially populated) instead of document ids. Singularity's terms-lookup against `_id` stops matching, its size-vs-count check throws (size N, matched M < N), and the archive build fails loudly rather than serving a wrong or empty download. But that check exists to catch a set whose materialized membership has drifted from its recorded size; it happens to catch this case too, it was not designed for it and should not be read as "Singularity validates the `path` value."

2. **Someone "fixes" the `path` literal itself, later, without knowing this.** Singularity's archive-cache dedup key is a hash of `{sqon, numSamples, lastUpdated}` only, verified directly in `SetQueryArchiveHashInfo`/`Archive.newFromSetQueryArchiveHashInfo` — it does not include `ids` or `path`. If a fix changes `path` to something that still resolves to the same document ids (e.g. explicitly targeting `_id`, which is what already happens today via the fallback), the sqon, count, and `lastUpdated` are all unchanged, the hash is identical, and `saveAndTriggerBuildOrGetArchiveFunctionForSetId` serves the old cached archive via `ExistingArchiveRestartException` without rebuilding anything. The fix would look like it worked, byte-identical output, while never actually having been exercised. Verifying a future fix to this call site needs either a sqon that wasn't previously built, or the cached archive cleared first; rebuilding the same set proves nothing on its own.
fix: no urgent action on trigger 1, currently unreachable (the field doesn't exist) and fails loudly rather than corrupting downloads if it ever appears. Trigger 2 is the one to actually watch for: if anyone changes this `path` value for any reason, including as a "fix" prompted by this very entry, they must force a fresh build (new sqon or cleared cache) to confirm the change had any effect at all, not just rebuild the same set and see a matching download. The cleaner long-term fix is passing a `path` that's either genuinely meaningful (a real, always-populated unique field) or explicitly documented as a deliberate `_id`-fallback trigger, so the next reader doesn't have to redo this archaeology, and so a future "fix" doesn't get silently no-op'd by the cache.
standalone: yes
